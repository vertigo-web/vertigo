# vertigo 0.13.0 release notes

Two things were rebuilt in this release: the reactive graph, and keyed list rendering.
A third, smaller change makes printing a type into the DOM opt-in rather than automatic.

The [changelog][changelog] lists every change as a single line. This document carries
the reasoning behind the breaking ones, the migration steps, and the mechanism behind the
performance numbers.

See also the [reactive graph guide][reactive-graph], the
[collection guide][collections] and the [invariants][invariants].

## Migrating

### The reactive graph

The graph is now transactional and has an equality cutoff: a node recomputes when its
dependencies change rather than on the next read, and a value that compares equal to the
previous one notifies nobody.

**`Computed<T>` requires `T: PartialEq` everywhere.** It was previously required only by
`subscribe`. The cutoff needs it on every node, so a `Computed` over a type without
`PartialEq` no longer compiles. Derive it, or wrap the payload in a newtype that compares
the part which actually matters.

**A `Computed` recomputes eagerly.** It used to be lazy, recomputing on the next read.
Reading through `transaction(|ctx| ...)` now serves the cached value. Code which relied on
a read to trigger the recompute — for instance a compute closure with a side effect that
was expected to run at read time — no longer sees it happen there.

**`Computed::subscribe_all` is gone.** Unchanged values no longer notify anybody, so it has
nothing left to report. Use `subscribe`.

**`Dependencies` is gone.** Use `transaction`, `Driver::transaction` and
`Driver::on_after_transaction`.

**Writing from the wrong place is now ignored rather than fatal.** `Value::set` from a
compute closure, a `subscribe` callback, or a `DropResource` destructor is refused. It used
to panic with *"You cannot change the source value while the dependency graph is being
refreshed"*; the write is now ignored and reported through `log::error!`, so one misplaced
write no longer takes the application down. The check follows the call stack, so it covers
a `Drop` that runs inside such a callback.

Writing from event handlers, timers, fetch, `on_after_transaction` and `when_connect`
(`create`) is unaffected. The full set of rules, and where you may write, is in
[`reactive::invariants`][invariants].

**`when_connect` and `Value::with_connect` moved out of the refresh.** The closure now runs
after the wave that made the node watched — and after `on_after_transaction` — instead of
in the middle of a refresh, and the resource is dropped after the wave that unwatched it.
`create` may write. The destructor must only tear down the external handler; a write from
it falls under the rule above.

### Printing a type into the DOM: `DomDisplay`

`EmbedDom` used to be implemented for every `T: ToString`, by value and by reference, and
`AttrValue` was built from every `T: ToString` in the same way. Both blanket impls are gone.
Printing is now opt-in per type through the new `DomDisplay` trait:

```rust
impl vertigo::DomDisplay for Route {}
```

That one line is the whole migration for a printable type of your own, and it covers more
than the blanket impl did: `Route` and `&Route` as an attribute value and as embedded text,
plus `Computed<Route>`, `Value<Route>`, their `Option` variants, and references to those.
So both of these work from the single impl:

```rust
dom! { <a href={my_route}>{my_route}</a> }
```

What did not need migrating:

* the primitives are opted in already
* the string types embed as before
* a reactive wrapper still embeds anything printable, so `Computed<MyType>` is unaffected
* the types behind the `chrono` and `rust_decimal` features are opted in by vertigo, because
  an application cannot write those impls itself: `NaiveDate`, `NaiveTime`, `NaiveDateTime`,
  `DateTime<Tz>` and `Decimal`

Why opt-in at all: the blanket impl claimed every printable type, which meant a type that
renders real DOM had to compete with it. Such a type now implements `EmbedDom` directly
without that competition — and a type asking for both is a coherence error, which is the
intended signal rather than an accident.

`IntoAttrValue` is the bound that `DomElement::attr` and the `dom!` macro use for attribute
values. It is `Into<AttrValue>` with a blanket impl, so there is nothing to implement; it
exists so that a value with no conversion produces an error saying what to write.

`AttrValue` itself gained a `Static(&'static str)` variant, and `AttrValue::get` returns the
new `AttrText` rather than `Rc<String>`.

### Keyed lists

Keyed rendering is rebuilt around per-key `Computed`s — one `Computed` per key, reused for
that key across updates, in the style of Solid's `<For>`. The new entry point is
`keyed_computed_list`, with `KeyedListItem` as the item type.

`ValueSynchronize`, `Value::synchronize`, `LazyCache::synchronize` and
`CacheValue::synchronize` are gone, as are `Collection` and `CollectionModel`. All are
superseded by `keyed_computed_list`. `CollectionKey` stays. The guide
`guides::value_synchronize_and_collections` is replaced by [`collections`][collections].

Signature changes:

* `render_list` takes a `Vec<T>` source, its render closure receives `&Computed<T>` instead
  of `&T`, and the key type must implement `Debug`
* the render closures of `render_list_memo` and `render_resource_list_memo` receive
  `&Computed<T::Value>`; `Loading` and `Error` render as an empty list
* the mount closure of `DomComment::new_marker` takes a third argument, `&MarkerContent`,
  which lets a marker comment report the nodes it keeps in front of itself. A marker moved
  within the same parent no longer re-runs its mount

`RenderValue` is the trait form of `render_value` / `render_value_option`, for generic code
which needs to be written once over either.

#### DOM shape changes

Two changes are invisible in the browser but visible to a test which asserts on rendered
HTML:

* every `render_list` row is preceded by an anchor comment node
* a reactive value embedded in `dom!` — `<span>{my_value}</span>` — updates its text node in
  place instead of replacing it, so `<li>{value}</li>` no longer emits a trailing
  `<!-- v -->` inside the element

### The DOM command wire format (`dev`)

DOM commands travel to the browser in a flat binary format instead of as `JsJson` objects.
`CommandForBrowser::DomBulkUpdate` therefore carries `commands: Vec<u8>` rather than
`list: Vec<DriverDomCommand>`. Encode and decode with
`dev::command_wire::{encode_dom_commands, decode_dom_commands}`.

Nothing above the wire changed — the same commands are emitted in the same order. What
changed is the cost: every command used to require two `BTreeMap`s and three heap `String`s
to build, serialize and drop, and repeated its field names on the wire once per command.
Element and attribute names are now interned per batch.

Related, and visible to anything decoding vertigo's own encoding: `AutoJsJson` now encodes a
`Vec<u8>` field of an enum variant as `JsJson::Vec` — one length-prefixed byte run — which is
what it already did for a struct field of that type. It previously produced a list with a
`JsJson::Number` per byte.

## Performance

### Keyed list reconciliation

The largest win. Reordering a keyed list now moves only the rows whose order actually
changed. The keyed phase used to re-insert every row it walked, so swapping two rows of a
thousand moved the 998 rows between them; it now moves two. Measured on the
`js-framework-benchmark` swap workload: **179ms to 32ms**.

Alongside that, updating one row no longer costs work proportional to the *square* of the
list length, and `keyed_computed_list` builds one index per update instead of three,
stamping a single key cache instead of rebuilding two.

### Hashing

Vertigo's own hash maps — the keyed-list index, the list reconciler's middle cache, and every
`dev::HashMapMut`, including the one consulted for each DOM insertion — use an FxHash hasher
instead of the standard `SipHash-1-3`. Worth about a fifth of the keyed-list improvement
above.

FxHash is **not** collision-resistant against chosen keys. The worst case is a render that
degrades to quadratic on a list keyed by attacker-chosen strings, which matters server-side
under SSR and not in the browser. `dev::HashMapMut` gains a defaulted hasher parameter, so a
map that wants `RandomState` can still say so.

### Cheaper elements

Three changes to how an element carries its attributes:

* an element only builds a class merger when it has two sources to merge. It used to build
  one always: 160 bytes behind an `Rc` on every element
* the merger itself is smaller and quieter, the `css` half is boxed so only elements using
  css carry it, and the resolved css class name is cached rather than re-derived whenever the
  class attribute moves
* only `class` goes through that merger now. Every other attribute is recognised when the
  element is built rather than on every write, and talks to the driver directly, so a
  reactive `href` no longer clones an `Rc` into its subscription

`DomElement::attr_static` is new, and the `dom!` macro emits it for an attribute whose name
and value are both literals — `class="col-md-1"`, `aria-hidden="true"`.

### Text updates in place

A reactive value embedded in `dom!` updates its text node rather than replacing it —
**3x faster**. `DomText::new_computed` creates its node with the value already set rather
than empty, and gained a `new_computed_display` sibling for `T: ToString` (`u32`, `bool`,
your own `Display` types) alongside the existing `T: Into<String>` form.

Note the [DOM shape change](#dom-shape-changes) this implies for tests.

### Smaller wasm

Two whole subsystems now link only when the application actually reaches for them. Both are
measured on `examples/counter` — a release build through `wasm-opt -Os` — by building the same
app with and without the thing:

| counter | raw | gzipped |
| --- | --- | --- |
| no `css!`, no fetch | 181,123 | 67,389 |
| one `css!` added | 211,750 | 80,317 |
| eager fetch-cache decode | 216,323 | 80,971 |

* an application that uses no `css!` no longer links the css engine: **~30 kB raw, ~13 kB
  gzipped** off a small application, and 16% off first paint. **An application that does use
  `css!` keeps the engine and sees no size change**
* the SSR fetch cache is decoded on first use rather than at startup, so an application with
  no `LazyCache` never mentions it and the linker drops the whole decode path — **~34 kB raw,
  ~13 kB gzipped**. `get_response` is the only caller and `LazyCache::new` is its only call
  site, so nothing reaches it in an application that fetches nothing
* `AutoJsJson` builds an object one field at a time through a shared function instead of with
  `BTreeMap::from([..])`, and inserts the fields in key order. Saves 1-5% of the wasm,
  depending on how many types the application derives. Encoding an enum gets faster and
  encoding a struct slightly slower; the browser benchmark sees neither
* `vertigo new` now writes a `[profile.release]` into the project it generates. The fullstack
  template additionally splits `opt-level` per target through `.cargo/config.toml`, so the
  frontend is built for size and the backend for speed

### Fewer copies in the graph

`Value::new` and `Value::set` no longer deep-copy the payload when nothing is listening for
`Value::add_event`. A compute closure reading the same value repeatedly records it once, and
recomputing a node with many dependencies is no longer quadratic in their number.

## Correctness fixes worth knowing about

Beyond the list in the changelog, two of the fixes describe behaviour you may have worked
around:

**A node is computed at most once per change, whatever the shape of the graph.** A `get`
during propagation refreshes a stale parent before returning, so unequal path lengths and
conditionally read parents no longer recompute a join once per path — and a subscriber cannot
observe a value assembled from a half-updated graph.

**Rows survive a reorder.** `render_list` used to corrupt sibling order when reordering or
inserting rows whose root is a plain element rather than a `render_value` marker. Moving a
row now repositions its DOM instead of rebuilding it, so input values, listeners and children
survive.
