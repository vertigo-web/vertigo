# vertigo 0.14.0 release notes

Websockets report why they closed, carry binary frames and reconnect after a growing wait.
Elements get pointer and wheel events and `<canvas>` drawing, and a page rendered on the server
can use the user's languages and the cookies the app names.

Two changes need attention when upgrading. [`WebsocketMessage`](#websocketmessage) changed, and
the compiler shows where. [Every event from the browser runs in one
transaction](#one-event-one-transaction) now, and nothing shows where that matters: a handler
that writes a value and then reads something computed from it, or looks into the DOM, sees them
as they were before the event.

The [changelog][changelog] lists every change as a single line. This document carries the
migration steps, the reasoning behind the breaking changes and a short example of each new
feature. The [API docs][docs] have the details.

## Migrating

### One event, one transaction

Every event from the browser - a DOM event, a websocket message, a fetch response, a timer, a
frame to draw, a change of the location, and with the timer every step of async code - runs in
one transaction. Whatever the app writes in it propagates once, when the event's code returns,
and reaches the DOM in one batch. Before, each `Value::set` was a transaction of its own, so a
websocket message setting a value per row of a table sent the browser a batch of DOM changes
per row.

Code that reads back what it wrote, in the same handler or the same step of async code (between
two `.await`s), sees two differences.

**A `Computed` keeps its value from before the event.** A `Value` is always current, but a
`Computed` that something watches - f. ex. it's on the page - is refreshed when the transaction
ends, and until then `get` returns what it had:

```rust
let count = Value::new(1);
let doubled = count.map(|count| count * 2);

let on_click = bind!(count, doubled, |_| {
    count.set(5);
    // 10 in 0.13. Now still 2, if something watches `doubled`.
    let shown = transaction(|ctx| doubled.get(ctx));
});
```

Compute it from the `Value` instead - `count.get(ctx) * 2` - or leave it to the graph: whatever
is computed from `doubled`, the DOM and the `subscribe` callbacks get 10 once the transaction
ends. The [invariants][invariants] have the rules.

**The DOM changes after the event.** `js!` reaches the browser at once, so after a write it finds
the DOM from before the event: a row the write adds isn't there to scroll to yet, and an element
it renders isn't there to focus.

```rust
lines.change(|lines| lines.push(line));
// The new line isn't on the page yet, so this scrolls to where the list ended before
js! { #list_ref.scrollTo(0, 1_000_000) };
```

Run it in a spawned future instead. Its first step runs on a timer, after the event's changes
reached the DOM:

```rust
lines.change(|lines| lines.push(line));
let list_ref = list_ref.clone();
get_driver().spawn(async move {
    js! { #list_ref.scrollTo(0, 1_000_000) };
});
```

To focus an element the write renders, give it `autofocus`: the driver focuses it after the
batch that puts it on the page.

### `WebsocketMessage`

`WebsocketMessage::Close` carries a [`WebsocketClose`][WebsocketClose], and binary frames come as a
new variant, `Binary`:

```rust
// 0.13
WebsocketMessage::Close => connection.set(None),

// 0.14
WebsocketMessage::Close(_) => connection.set(None),
WebsocketMessage::Binary(_) => {}
```

`Close` now comes also when an attempt to connect fails, with `was_connected: false` and code 1006.
In 0.13 the app heard nothing of a failed attempt. A handler that takes every `Close` for the end
of a connection it had - f. ex. to show "Connection lost" - should check `was_connected`.

## New features

### Websockets

[`WebsocketClose`][WebsocketClose] tells why a websocket closed: the close `code` and `reason`,
and `was_connected`. When the server closed it with a code of the app's own, f. ex. for a session
that ended, `stop_reconnecting` gives up on the websocket.

After a close, a websocket connects again after a random 0.5-1 s, doubled with each failed attempt
up to 15-30 s - in 0.13, every 3 s. Clients cut off together, f. ex. by a restart of the server,
don't all come back at once. [`WebsocketOptions`][WebsocketOptions] with
`Driver::websocket_with_options` change the waits and the timeout to connect.

Binary frames come as `WebsocketMessage::Binary(Vec<u8>)`, and `WebsocketConnection::send_binary`
sends one. In 0.13 the driver dropped them with an error.

```rust
let options = WebsocketOptions {
    reconnect_delay: 500,
    ..WebsocketOptions::default()
};

// Open while `socket` lives
let socket = get_driver().websocket_with_options("wss://example.com/live", options, |message| {
    match message {
        WebsocketMessage::Close(close) if close.code == 4001 => {
            // The app's own code: the session is over, connecting again won't help
            close.stop_reconnecting();
        }
        WebsocketMessage::Connection(connection) => connection.send_binary(vec![1, 2, 3]),
        WebsocketMessage::Binary(bytes) => log::info!("{} bytes", bytes.len()),
        _ => {}
    }
});
```

`--proxy` of `vertigo serve` and `vertigo watch` carries websockets too, so an app in `watch`
reaches its backend's websockets through the same proxy as its API:
`--proxy /api=http://127.0.0.1:8000/api` covers `/api/ws` too. In 0.13 the handshake hung there.

### Pointer and wheel events

`on_pointer_down`, `on_pointer_move`, `on_pointer_up` and `on_pointer_cancel` give a
[`PointerEvent`][PointerEvent] for a mouse, a pen or a finger alike. `capture_pointer` keeps the
pointer's events coming to the element until it's released, even outside the element - what a
drag needs:

```rust
let position = Value::new((40.0, 40.0));
// The point of the box the pointer holds, while dragging
let grab = Rc::new(Cell::new(None::<(f64, f64)>));

let down = bind!(grab, |event: PointerEvent| {
    event.capture_pointer();
    grab.set(Some((event.pointer_x, event.pointer_y)));
});

let moved = bind!(grab, position, |event: PointerEvent| {
    if let Some((grab_x, grab_y)) = grab.get() {
        position.change(|(x, y)| {
            *x += event.pointer_x - grab_x;
            *y += event.pointer_y - grab_y;
        });
    }
});

let up = bind!(grab, |_: PointerEvent| grab.set(None));

let style = position.map(|(x, y)| {
    format!("position: absolute; left: {x}px; top: {y}px; touch-action: none;")
});

dom! {
    <div
        style={style}
        on_pointer_down={down}
        on_pointer_move={moved}
        on_pointer_up={up.clone()}
        on_pointer_cancel={up}
    >
        "Drag me"
    </div>
}
```

`touch-action: none` keeps the browser from taking a finger on the element to scroll the page,
which would end the drag with `on_pointer_cancel`.

`on_wheel` gives a [`WheelEvent`][WheelEvent]: how far the wheel or the touchpad moved and in what
unit, where the pointer is, the modifier keys and `prevent_default` - f. ex. to zoom instead of
scrolling the page:

```rust
let on_wheel = bind!(zoom, |event: WheelEvent| {
    if event.ctrl_key {
        // Ctrl with the wheel, or a pinch on a touchpad
        event.prevent_default();
        let factor = (-event.delta_y / 200.0).exp();
        zoom.change(|zoom| *zoom = (*zoom * factor).clamp(0.5, 8.0));
    }
});
```

### Drawing on a canvas

`draw` on a `<canvas>` takes a [`Drawing`][Drawing], or a `Value` or `Computed` of one: operations
of the 2D context recorded in Rust. A new drawing clears the canvas and goes in the same batch as
the rest of the DOM changes, and one equal to the last isn't sent again.

A drawing is in the units of a `ViewBox`, fitted into the canvas like SVG's `xMidYMid meet`, or in
CSS pixels. Widths and radii can also be given in CSS pixels (`line_width_px`, `fill_circle_px`),
the same however big the drawing is shown. The canvas takes its size from CSS and keeps its
bitmap at that size times `devicePixelRatio`, so the drawing stays sharp.

```rust
let points = Value::new(vec![(0.0, 60.0), (25.0, 20.0), (50.0, 40.0), (75.0, 10.0), (100.0, 30.0)]);

let chart = points.map(|points| {
    // 0-100 both ways, with a margin
    let mut drawing = Drawing::new(ViewBox::new(-10.0, -10.0, 120.0, 120.0));
    drawing
        .fill_style("#eee")
        .fill_rect(0.0, 0.0, 100.0, 100.0)
        .stroke_style("steelblue")
        .line_width_px(2.0)
        .polyline(points);
    drawing
});

dom! { <canvas style="width: 100%; height: 200px;" draw={chart} /> }
```

### Animation frames

[`Driver::on_animation_frame`][on_animation_frame] calls back before every frame the browser
draws, with the time of the frame, until the returned `DropResource` drops. All such callbacks of
a frame run in one transaction, so what they change reaches the DOM in one batch. Given to
`Value::with_connect`, it runs only while something shows the value:

```rust
// Seconds since the dot appeared, counted while something shows them
let seconds = Value::with_connect(0.0_f32, |seconds| {
    let seconds = seconds.clone();
    let start = Cell::new(None);

    get_driver().on_animation_frame(move |time| {
        let first = start.get().unwrap_or(time);
        start.set(Some(first));
        seconds.set(((time - first) / 1000.0) as f32);
    })
});

let drawing = seconds.map(|seconds| {
    // Once round every three seconds
    let angle = seconds * std::f32::consts::TAU / 3.0;

    let mut drawing = Drawing::new(ViewBox::new(-100.0, -100.0, 200.0, 200.0));
    drawing
        .fill_style("tomato")
        .fill_circle(80.0 * angle.cos(), 80.0 * angle.sin(), 12.0);
    drawing
});

dom! { <canvas style="width: 200px; height: 200px;" draw={drawing} /> }
```

### The user's language and cookies during SSR

[`Driver::languages`][languages] gives the languages the user prefers, the most preferred first:
`navigator.languages` in the browser, and the request's `Accept-Language` while the server renders
the page - browsers send it from the same list. A page that picks its language from them comes
from the server in the language the browser will show it in.

A cookie named with `--ssr-cookie` of `vertigo serve` and `vertigo watch`, or with
[`MountConfigBuilder::ssr_cookie`][ssr_cookie] in an actix-web server of your own, reads with
`cookie_get` and `cookie_get_json` while the server renders the page too - f. ex. the language
the user picked. The others read as empty there, as before. Only for cookies the browser shows
the app: an `HttpOnly` cookie would make the server render what the browser can't.

With `Lang::from_tag` turning a tag like `pl-PL` into a language the page has:

```rust
// The language the user picked before, or the first one the browser prefers that the page has
let picked = get_driver().cookie_get("lang");
let lang = Lang::from_tag(&picked)
    .or_else(|| get_driver().languages().iter().find_map(|tag| Lang::from_tag(tag)))
    .unwrap_or(Lang::En);
```

```sh
vertigo serve --ssr-cookie lang
```

`vertigo_install` passes both headers on by itself. A server that calls `ServerState` directly
passes them with `ServerState::request_with_headers` and `RequestHeaders`, and
`request_accept_language` reads `Accept-Language` from an actix-web request.

### Default component props

A param of a [`#[component]`][component] can declare a default, `#[default = <constant>]`, and
`{..}` in its tag fills the props left out:

```rust
#[component]
fn Avatar<'a>(name: &'a str, #[default = 48] size: u32, #[default = "50%"] radius: &'a str) {
    let style = format!("width: {size}px; height: {size}px; border-radius: {radius};");
    dom! { <div style={style}>{name}</div> }
}

dom! { <Avatar name="Ann" {..} /> }
```

`{..}` needs a compiler with default field values
([rust-lang/rust#132162][default-field-values]) - for now nightly, with
`#![feature(default_field_values)]` in each crate using `{..}`; the crate declaring the component
doesn't need it. Other compilers ignore the defaults, so every prop has to be given there.

## Fixes worth knowing about

Beyond the list in the changelog, a few of the fixes describe behaviour you may have worked
around.

**Websockets close with their page.** A page kept in the browser's back/forward cache kept its
websockets open, so the server went on sending to a page nobody saw. Now they close when the page
goes into the cache - the app gets `Close` - and connect again at once when it comes back, with a
new `Connection`. A websocket dropped while still connecting, f. ex. as its component left the
page, connected anyway and stayed open until the page went away. Now dropping it aborts the
connection.

**Dropping a handle from `when_connect` doesn't panic.** A `Computed` whose `when_connect` closure
held the last handle of another `Value` or `Computed` panicked when it went ("RefCell already
borrowed"), and so did an `on_after_transaction` callback holding the `DropResource` of another
one.

**`render_value` right under `<html>` survives hydration again.** Since 0.13.4 a `render_value`
or `render_list` right under `<html>` - f. ex. one that swaps `<body>` once the user logs in -
broke the page after hydration ("InsertBefore" `NotFoundError`).
